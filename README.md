# 1С:Предприятие 8.3 — пакет для Nix/NixOS

Дистрибутив 1С скачивается с портала как zip-архив (например
`server64_8_3_27_2130.zip`). Внутри него лежит самораспаковывающийся
установщик InstallBuilder (`setup-full-*.run`), который жёстко требует
root и пишет служебный файл в `/usr/local/bin` в обход `--prefix`.
Оказалось, что распаковка архива, поиск инсталлятора внутри него и запуск
без root прекрасно решаются **внутри обычной, воспроизводимой песочницы
`nix build`**, без отдельных скриптов и без ослабления sandbox:

- сам архив распаковывается прямо в `installPhase` через `unzip`, а
  инсталлятор (`setup-full-*.run`) внутри него находится через `find` —
  пользователю не нужно ничего распаковывать вручную заранее.
- geteuid() == 0 — проходит через непривилегированный user namespace
  (`unshare --user --map-root-user`); настоящих привилегий процесс не
  получает.
- запись в /usr/local/bin — корень песочницы и так принадлежит
  пользователю сборки, достаточно `mkdir -p /usr/local/bin`.
- сам инсталлятор — обычный (не-NixOS) ELF с интерпретатором
  `/lib64/ld-linux-x86-64.so.2`, которого в песочнице нет: подкладываем
  туда симлинк на загрузчик glibc из nixpkgs.

Всё это — обычные шаги `installPhase` в `package.nix`, никакого
`__noChroot`, никакого внешнего `.sh`.

## Компоненты и язык — прямо из архива

Список допустимых значений для `--enable-components` не хранится в
Nix-файле как константа: `package.nix` распаковывает архив, вызывает
`setup-full-*.run --help --installer-language en` во время сборки и
парсит из вывода актуальный на данный момент список (строка
`Allowed: ...`). Если 1С в новой версии дистрибутива добавит/уберёт
компонент — ничего в `package.nix` менять не нужно, разве что переименуют
сами компоненты.

(Разбор идёт по английскому выводу, а не по языку `language`: без
локали внутри песочницы кириллица в тексте инсталлятора превращается в
`?????`, тогда как английский текст — чистый ASCII.)

## Использование пакета напрямую

```console
$ nix-instantiate --eval -E 'builtins.pathExists "/путь/к/server64_8_3_27_2130.zip"'
```

```nix
let
  pkgs = import <nixpkgs> { config.allowUnfree = true; };
  mkOnec = pkgs.callPackage ./package.nix { };
in
mkOnec {
  archiveFile = "/home/user/Downloads/server64_8_3_27_2130/server64_8_3_27_2130.zip"; # строка!
  # "ru" здесь обязателен: язык интерфейса — отдельный компонент
  # инсталлятора, а не встроенный по умолчанию функционал (см. ниже).
  # module.nix добавляет его сам из services.onec.language; при прямом
  # использовании package.nix — нужно руками.
  components = [ "server" "server_admin" "ws" "ru" ];   # или [ "client_thin" "ru" ], [ "client_full" "ru" ]...
  language = "ru";
  version = "8.3.27.2130";
  pname = "1c-enterprise-server";
}
```

`archiveFile` — именно **строка**, не путь-литерал: если каталог с
архивом содержит нелатинские символы (например, `~/Загрузки`), парсер
Nix ошибается на путях-литералах вида `/foo/бар/baz`. Внутри
`package.nix` строка сама конвертируется в путь через
`/. + toString archiveFile`, а сам архив распаковывается и инсталлятор
внутри него находится уже во время сборки.

Собранный пакет кладёт файлы в `$out/opt/1cv8/x86_64/<version>/` (как и
штатная установка — 1С сам ищет свои ресурсные файлы `*_root.res`/
`*_root.hbk` рядом со своими `.so`, так что этот каталог менять на
`$out/lib` нельзя) и добавляет символические ссылки на основные бинари
в `$out/bin` (`ragent`, `rmngr`, `rphost`, `rac`, `ras`, `ibsrv`, `ibcmd`,
а для клиентских компонентов — `1cv8c` и т.п.).

При установке `package.nix` заодно убирает мусор, который тянет за собой
штатный инсталлятор и который в Nix-сборке не нужен и/или откровенно
битый:

- сам деинсталлятор и его файл данных (`uninstaller-full*`,
  `uninstallAsRoot`);
- многоязычную HTML-читалку инсталлятора (`readme.htm`, `readme/`);
- штатные шаблоны systemd-юнитов (`srv1cv8-*.service`, `ras-*.service`)
  — они прописывают FHS-пути (`/opt/1cv8/...`, `/home/usr1cv8`),
  нерабочие в Nix store, и не нужны: NixOS-модуль генерирует свои юниты
  с правильными путями (см. ниже).

Документация и лицензии (`docs/`, `licenses/`) при этом не удаляются, а
переносятся в `$out/share/doc/<pname>/` — общепринятое в Nix место,
вместо того чтобы лежать вперемешку с бинарниками и библиотеками.

`conf/conf.cfg` удаляется вместе с остальным мусором инсталлятора: это
служебный файл штатной утилиты обновлений (которой пакет не
пользуется), и вдобавок битый — в нём прописан путь временной песочницы
сборки (`ConfLocation=/build/install-root/opt/1cv8/conf`), которого
после сборки не существует. Ключ `SystemLanguage` в этом файле выглядит
как настройка языка интерфейса и упоминается так в некоторой
документации/форумах — но экспериментально (четыре комбинации:
`RU`/`EN`/пусто × русская/английская локаль хоста, оба места файла —
версионное и общее) подтверждено, что на этот конкретный лаунчер он
**не влияет вообще**. Реальный механизм — компоненты, см. ниже.

### Язык интерфейса (включая стартовый лаунчер) — отдельный компонент

Русский (как и любой нелатинский) язык интерфейса — это не встроенный по
умолчанию функционал, а **отдельный устанавливаемый компонент
инсталлятора**: сам инсталлятор ставит по умолчанию
`client_full,langs,en,ru,advanced` (строка `Default:` в его `--help`),
но `package.nix`/`module.nix` явно ограничивают набор компонентов
(`server`, `server_admin`, `ws`, `client_thin` и т.п.), и в этот
явный список язык не входит. Без соответствующего компонента в сборку
физически не попадают файлы с переводом интерфейса (`*_ru.res`,
`*_ru.hbk`, включая `1cv8s_ru.res` — ресурсы именно стартового
лаунчера) — и тогда ни `LANG`, ни `conf.cfg`, ни `/L` не помогают,
потому что переводить нечем.

Поэтому `module.nix` сам добавляет код `services.onec.language` (по
умолчанию `"ru"`) в список компонентов и для сервера, и для клиента —
включая стартовый диалог выбора информационных баз, который тоже
локализуется этим компонентом (`"langs"` из строки `Default:` — не
настоящий компонент, `--enable-components` его не принимает; настоящий
переключатель — код языка, например `"ru"`). При использовании
`package.nix` напрямую (без модуля) компонент нужно добавлять в список
`components` вручную.

Проверено эмпирически: после добавления компонента `"ru"` язык
интерфейса устанавливается сам, без какого-либо участия `LANG` или
`conf.cfg` — платформа, похоже, просто использует единственный
установленный нелатинский языковой компонент, не сверяясь ни с локалью
хоста, ни с конфигом.

Дополнительно `LANG`/`LANGUAGE` в обёртке клиента (`preFixup`) не
фиксируются жёстко — наследуются из окружения запуска, задаётся только
`LOCALE_ARCHIVE` (без него `setlocale()` с nix-glibc не находит вообще
никаких локалей и откатывается на `C`/`POSIX`).

### Толстый клиент (`client_full`) и Wayland

Толстый клиент — `1cv8` (с Конфигуратором, в отличие от тонкого
`1cv8c`) — сам инициализирует EGL для своего 3D/чартового рендера, в
обход выбора GTK-бэкенда: если в окружении есть `WAYLAND_DISPLAY`, он
безусловно пытается получить EGL-дисплей под Wayland и падает в цикл
`Could not create default EGL display: EGL_BAD_PARAMETER` ещё до
создания окна (воспроизведено на реальном Wayland-сеансе). Задать
`GDK_BACKEND=x11` недостаточно — эта проверка внутри 1С смотрит только
на `WAYLAND_DISPLAY`. Поэтому `package.nix` безусловно гасит
`WAYLAND_DISPLAY` в обёртке для всех клиентских бинарников
(`gappsWrapperArgs+=("--unset" "WAYLAND_DISPLAY")`) — тонкий клиент
`1cv8c` при этом просто уходит на XWayland, что не влияет на его работу.

## Зависимости

Почти всё (libstdc++, ICU, tcmalloc, libssh, ImageMagick и т.д.) 1С
приносит в комплекте — `autoPatchelfHook` просто чинит интерпретатор и
сшивает эти файлы между собой. Из внешнего окружения реально нужны:

- **glibc, krb5, keyutils, e2fsprogs** — всегда (glibc — рантайм,
  krb5/keyutils — под GSSAPI в бандловском libssh.so, e2fsprogs — потому
  что этот libssh слинкован со старым SONAME `libcom_err.so.2`, а не с
  тем, что даёт krb5 в nixpkgs).
- **glib, gdk-pixbuf, cairo, pango, atk, gtk3, cups, libGL,
  webkitgtk_4_1** — только если среди `components` есть что-то с
  префиксом `client_` (GUI тонкого/толстого клиента, включая встроенный
  HTML-движок). Для чисто серверных сборок это не подключается вовсе.

## NixOS-модуль

```nix
{
  imports = [ ./nix/module.nix ];

  services.onec = {
    enable = true;
    archiveFile = "/home/user/Downloads/server64_8_3_27_2130/server64_8_3_27_2130.zip";
    language = "ru";

    server = {
      enable = true;
      components = [ "server" "server_admin" "ws" ];
      ras.enable = true;      # rac/ras — консоль администрирования кластера
      openFirewall = true;
    };

    client = {
      enable = true;                        # добавить клиент в PATH всем пользователям
      components = [ "client_thin" ];       # или [ "client_full" ]
    };
  };
}
```

`services.onec.version` можно не указывать — по умолчанию она выводится
из имени файла в `archiveFile` (`server64_8_3_27_2130.zip`, версия
кодируется через "_" вместо ".").

Модуль заводит системного пользователя `usr1cv8`/`grp1cv8`, каталог
данных кластера `/var/lib/1cv8` (через `StateDirectory`) и юниты
`1c-ragent.service` / `1c-ras.service`, повторяющие по смыслу штатные
`srv1cv8-*.service` / `ras-*.service` из дистрибутива, но с путями,
пригодными для Nix store. `services.onec.client.enable` просто кладёт
клиентский пакет в `environment.systemPackages` — это не сервис.

## Важно про лицензию

Дистрибутив 1С:Предприятие — проприетарное ПО. Пакет здесь не
переопубликовывает и не скачивает его откуда-либо: он лишь берёт уже
скачанный вами (под вашей лицензией с сайта 1С) архив дистрибутива и
превращает его в воспроизводимую Nix-сборку. Указывать в `archiveFile`
можно и нужно только файл, на который есть лицензия; сам архив и всё, что
из него собрано, публиковать в открытом доступе нельзя.
